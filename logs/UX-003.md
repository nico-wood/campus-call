# Closed account access and real local waitlist — 14 November 2026

## User request and resulting flow

The user explicitly requested that Confirm explain that sign-in is required, that attempting sign-in lead to a professional registration-closed page, and that Join the waitlist collect a name and email and append them to a list.

The resulting path is: example Confirm → focused “Continue to sign in” action → `/login` (“Registration is currently closed.”) → `/waitlist` → server save → “You’re on the waitlist.” Settings also links to account access. There is no working sign-in or new account creation in this flow. Example confirms still call the unchanged no-write module; they spend no virtual credits and add no points. They make no network request. The waitlist form is the separate explicit write action.

## Persistence and boundaries

- `POST /api/waitlist` stores normalized name, lowercase email, and an ISO join timestamp in private `.data/waitlist.sqlite`.
- Native `node:sqlite` is tested on Node 24.11.1; it emits its experimental API notice. It adds no package dependency. SQLite is local server persistence across connections/restarts, not a browser-only success state.
- The database's case-insensitive primary key prevents duplicate email entries and preserves the first record. SQL is parameterized. New and duplicate submissions return the same generic success response.
- The API bounds the body at 4096 bytes, validates JSON/content type/name/email server-side, checks request Origin against the HTTP host, and exposes no list-read endpoint. Errors never return subscriber values or database exception details. Responses are `no-store`.
- A production browser check found that Next's internal request URL can use localhost while the browser uses 127.0.0.1. The origin check now matches the browser-facing HTTP Host, using the request protocol/forwarded scheme and allowing only HTTP/HTTPS. A regression test accepts the legitimate alias while rejecting an unrelated origin. See Next's bundled `data-security.md` origin/host guidance.
- `.data/` is gitignored; no subscriber data is committed or served as a public asset. The browser integration check creates a UUID email under example.invalid and removes only that synthetic row after verification. It never enumerates or changes real subscribers.
- This is explicitly a local preview. Vercel's server filesystem is not a durable hosted subscriber store. A hosted adapter/store must replace local SQLite before a public deployment collects names/emails. No hosted migration, Supabase file, grant, live session, or account module was changed by this task.

## UI states and accessibility

Both fields are visibly labeled, semantically required, and validated before sending a request. Invalid inputs focus the offending field. Pending submission disables repeat actions and reports busy state. Error responses preserve the form for retry and never show success. The new sign-in action receives focus when it replaces Confirm; the success status receives focus when it replaces the form. The native form fallback posts rather than putting names/emails in a GET URL.

The shared footer now stays at the bottom of short pages through a flexible workspace/main layout. Account headings balance their lines. All forms and account cards retain opaque surfaces over the forest/gold dither backdrop.
